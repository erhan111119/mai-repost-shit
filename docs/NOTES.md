# 实测数据与接口状态（NOTES）

本文件记录插件判据与接口的实测依据，供后续调参和排查用。数据采集于 2026-10-11。

## 一、艾特率判据的实测样本

每视频取最多 60 条评论（裸请求 3 页 × 20 条），统计含 `@` 的比例：

| 通道 / 分区 | 播放下限 | 有效样本 | 艾特率 |
|---|---|---|---|
| 鬼畜 tids=119 | 5 万 | 4/4 | 16.3% / 52.5% / **64.4%** / 66.1%（中位 64.4%） |
| 娱乐 tids=5 | 3 万 | 1/4 | 3.3% |
| 时尚 tids=155 | 3 万 | 1/2 | 23.3% |
| 搞笑 tids=138 | 1 万 | 1/4 | 0%~21.7%（多数视频评论不足 30 条） |

结论：判据成立且区分度强，但 **1万播放档的视频评论样本普遍不足**，
所以插件里把 `min_video_review` 前移到搜索阶段，并要求评论样本 ≥ `min_comments`。

## 二、「1万~10万 → 5万~30万播放」的检索配置实测

采样方式：4 个关键词 × 50 条，统计落在播放区间内的比例。

| 排序 | 时间窗 | 命中率 |
|---|---|---|
| `totalrank` | 72~336h | **18.0%** |
| `pubdate` | 36~168h | 6.0% |
| `pubdate` | 168~336h | 10.5% |
| `pubdate` | 336~720h | **23.0%** |
| `click` | 24~168h | **0%** |
| `click` | 72~336h | **0%** |

`click` 为 0 的原因：它只返回爆款（page1 就是 3000 万~1.3 亿播放），
且深翻页在 **~1400 万播放**处被截断（page=20 与 page=50 返回同一批），拿不到中间播放量。

加分区限定时命中率会更高（kw=搞笑 + tids=138 + 36~72h → 44~48%），
但本插件按要求不限定分区。

## 三、接口可用性

**免登录可用**

| 接口 | 说明 |
|---|---|
| `search/type` | 需先访问首页拿 `buvid3`；返回数值型 play/like/favorites/danmaku/video_review；支持 `order`/`pubtime_begin_s`/`pubtime_end_s`/`tids`/`duration` |
| `ranking/v2?rid=` | 每分区 100 条，stat 完整（249/250/251 返回 -400） |
| `view?bvid=` | 完整 stat + cid + tname + owner |
| `tag/archive/tags`、`view/detail` | 标签 |
| `x/v2/dm/web/seg.so` | 弹幕，未压缩 protobuf，content 在 **field 7** |
| `x/v2/reply/wbi/main` | 评论，wbi 签名 + 游标翻页，每页 20 条 |
| `x/player/playurl` | durl 模式（`fnval=1`）最高给到 **720P**（实测 tkhd 1280x720） |

**已失效**：`comment.bilibili.com/<cid>.xml`（0 条）、`x/web-interface/newlist`（空）、
`x/web-interface/dynamic/region`（-404）。

**wbi 签名**：`nav` 匿名可取 `wbi_img`（img_key + sub_key），按固定打乱表取 32 位 mixin key，
参数排序后 `md5(query + mixin_key)` 作 `w_rid`。仓库里另有一份实现可对照：
MaiBot 主仓库里的 `plugins/github_airlibrax_game-update-watcher/core/adapters/bili_dynamic.py`。

## 四、两个致命坑

1. **`buvid3` 会把评论接口打残**：带 `buvid3` 请求评论 → 每页 3 条且 `is_end=True`；
   不带任何 cookie → 每页 20 条、可游标翻页。曾据此误判「评论必须登录」。
   伪造 SESSDATA 与裸请求结果完全一致，所以**本插件不需要 SESSDATA**。
   实现上必须开两个 client：搜索带 cookie，评论裸请求。
2. **视频 CDN 校验 Referer**：必须 `https://www.bilibili.com/`，否则 403。

## 五、风控与限流

- 评论接口 6 连发（间隔 1.5s）全部 `code=0`；搜索 5 连发正常。
- 插件内做了 1.2s 全局请求间隔 + 每轮最多 `max_check_per_run` 条候选，
  一次 run 的请求量约为「4 次搜索 + 8×(1 详情 + 3 评论) + 1~2 次下载」，量级安全。

## 六、投递链路的两个约束

1. 视频段必须是 `{"type": "video", "file": "<本地路径>"}` 这种顶层键写法；
   写成 `{"type": "video", "data": {...}}` 时宿主会剥掉 `type`，适配器认不出。
2. 插件↔宿主 RPC 帧上限 **16MB**，base64 会膨胀 4/3 → 大文件必炸，所以一律用路径引用。

## 七、投稿命中率实测（决定关键词池与检查上限）

候选池 = 5万~30万播放 + 评论 ≥40 条 + 时长 ≤240s。

| 关键词池 | 候选 | 通过「艾特率 ≥50% 且评论 ≥30」|
|---|---|---|
| 偏主流搞笑（整活/抽象/沙雕/搞笑/离谱/逆天/名场面/迷惑行为） | 15（两轮） | **0 条**（最高 32%）|
| 泛鬼畜混合（鬼畜/抽象/整活/绷不住/答辩/逆天/难绷/离谱…） | 10~12 | **2 条**（58.3%、53.3%；另有一条 78%）|

翻页深度不是关键变量：取 3 页 / 4 页 / 5 页 / 6 页，通过数都是 2/10。
但个别视频会随深度上升（有个样本 1 页 0% → 6 页 56%），所以 3 页是性价比最好的档位。

结论：`max_check_per_run = 12` 时，一轮大约能挑出 2 条通过判据的候选；
候选排序按 `min(video_review, 300)` 降序（封顶是为了不让长合集靠评论数霸榜）。

## 九、自然语言点播的身份校验怎么做

Tool 回调里**拿不到点播者的真实 QQ 号**（群聊场景下工具回调的 `user_id` 恒为空，
这是宿主的既有行为）。但身份不是没法判——**入站钩子带真实发言者**，所以做法是：

1. 注册 `chat.receive.after_process`（`HookMode.BLOCKING` + `ErrorPolicy.SKIP`，只读不改写），
   把「会话 → 最近一位真人发言者」连同时间戳缓存起来（有 TTL，条目有上限）；
2. 工具触发时按 `stream_id` 回查，再跟 `[tool].whitelist` 比对。

两个必须知道的取舍：

- 缓存的是「该会话最近发言者」，不是「本次调用的发起者」。同一群多人抢话时会错位，
  所以白名单模式下**认不出发言者一律拒绝**（宁可少搬也不放过），而不是默认放行。
- 默认仍是 `permission = "anyone"`（群里谁都能点播），因为这是插件的使用场景本身；
  想收紧就改 `whitelist`。最严格是 `[tool].enabled = false`，只留管理员命令。
